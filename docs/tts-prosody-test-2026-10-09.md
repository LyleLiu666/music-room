# 短句收尾与停顿对照

## 已确认的结论

**声学收尾上下文方案已通过用户试听：结尾自然，中间也正常。** 固定样本由模型主动结束，未触及长度上限；相同中间输入在 C++ 与原版 PyTorch 中重现同样的末尾问题。只给波形还原模块补静音帧不足以补齐尾音；最终方案还在声学生成模块增加空白条件上下文，让末尾音节先生成完整，再还原波形。详见下文“采用的修复”。

用户指出正式服务生成的 `speech-v-1e5d7d54-05de-4c2c-b1e6-58cee3d32bd4.wav` 有严重的“掐断感”。这是本轮修复的原始反馈；有效 WAV、内存检查和播放测试不能代替听感验收。

该版本的原生日志记录 `text_chunk_count=1`、`text.segment_count=1`。全段 5.6889 秒，最长连续零采样仅一个采样点（22,050 Hz）；没有 200 ms 的拼接静音。当前驱动也没有二次裁切或拼接。因此，这个具体样本的问题不是多片段拼接造成的。后续分层对照把固定种子样本的主要尾部异常定位到有限声学序列缺少右侧上下文。原失败版本未保存种子，无法逐点重放其约 2 秒处的问题；新样本的中间表现已获用户确认。

## 参数对照

当前正式配置将 `num_beams` 设为 1；[audio.cpp v0.9.1 参数文档](https://github.com/0xShug0/audio.cpp/blob/v0.9.1/docs/models/index_tts.md) 的默认值为 3。恢复默认值是本轮验证候选，不能在试听前宣称它修复了问题。

在同一常驻原生进程中，固定参考 WAV、文本、情绪留空及随机种子 42，仅改变候选数量：

> 大家好我是迪丽热巴。在这个群里我最喜欢彪哥，爱你呦！

| 项目 | 当前参数 | 模型默认候选数 |
| --- | ---: | ---: |
| `num_beams` | 1 | 3 |
| 生成耗时 | 17.09 秒 | 23.25 秒 |
| 输出时长 | 4.89 秒 | 6.14 秒 |
| 原生进程物理峰值 | 4.8 GiB | 5.2 GiB |

样本为 `test-results/audio-cpp-trial/outputs/prosody-beams-{1,3}.wav`，完整参数与内存采样位于 `prosody-comparison.json`，波形检查位于 `prosody-wave-analysis.json`。使用已有常驻模型，没有重启正式服务或覆盖历史版本。数据来自本机 M4 / 32 GiB，每组一次；输出更长不等同于韵律更自然，也不能据此保证长文或 16 GB 实机结果。

## 用户试听与进一步定位

用户确认 A/B 中间断句都可以，**两组结尾都被掐断**；原正式样本约 2 秒处另有明显掐断感。因此本轮不切换候选数量，也不能把两份新样本的中间表现当成原样本没有问题的证明。

原样本最后一个采样为 -0.2552（满幅归一化）。最后 100 ms 先降至低能量，再在最后 20 ms 回升；三路候选同样在末尾低能量后出现突增。旧 PyTorch 的迪丽热巴短句也有相似末尾回升；其他音色的既有原生短句未统一出现同样强的边界。参考人声本身也在非零振幅结束。这些是可测的现象，尚不能确定来自参考条件还是波形还原边界，更不能证明约 2 秒处与末尾是同一原因。

诊断另制作 `original-tail-finished.wav`：原样本最后 80 ms 施加余弦收尾，并追加 180 ms 静音，既有文件和中间部分保持原样。它用于判断边界突变对听感的影响，不会补回模型可能漏掉的音节，正式输出暂未采用。

参考人声的尾部同样做上述处理后，复用同一原生进程、种子 42、一路候选重新生成 `reference-tail-test.wav`，耗时 17.76 秒、时长 5.36 秒；最后采样降至 0.0135，但最后 20 ms 仍有回升。单次输入对照不足以确定根因。完整记录为 `reference-tail-comparison.json`。

上述候选数量、参考淡出与输出淡出均未通过完整尾音试听，未作为最终修复；最终采用下面的声学上下文方案。

## 同一中间输入的分层复现

后续实验固定种子 42，采集原生引擎中间数据，分别重放各模块，避免把两次随机生成的差异误认为修复效果。诊断版基于 audio.cpp v0.9.1，仅增加采集；它生成的 PCM 与上面一路候选 A **逐字节相同**。

### 结束条件与长度

直接记录选中候选的 `finished` 状态：模型主动选择了结束标记，实际声音编码 245 个，上限 1,500 个。原生日志 `generated_stop_seen=0` 具有误导性：代码先排除了结束标记，再在已排除的编码中查找，因此不能据此判断触及长度限制。

245 个编码按原版同样的 `floor(245 × 1.72)` 得到 421 帧声学内容。C++ 与原版的参考段切除及输出帧数逻辑一致，代码检查未发现多切尾部帧。模型主动停止不等于最后一个音节已自然收尾。

### 声学内容生成（S2Mel）

采集同一份条件、参考频谱、音色向量和初始噪声，在原 PyTorch 的 `solve_euler` 中重放相同 25 步、CFG 0.7。输出都是 421 帧，频谱平均绝对差 0.000942，相关系数 0.999999866；最后一帧峰值分别为 0.1271 / 0.1291，都有同样的末尾回升。这组输入下，没有证据显示声学模块的 C++ 移植额外引入了明显尾部差异。

该实验复用了原生引擎前段生成的条件，**不等于整个 Python 与 C++ 流程已经逐层验证**；声音编码生成、参考特征与条件构造仍在排查范围内。

### 波形还原（BigVGAN）

把完全相同的 421 帧频谱分别交给 C++ 与原版 PyTorch BigVGAN：

| 输入与实现 | 最后 20 ms 的 RMS | 输出时长 |
| --- | ---: | ---: |
| 原频谱，C++ | 0.078590 | 4.8878 秒 |
| 原频谱，PyTorch | 0.079431 | 4.8878 秒 |
| 原频谱末尾补 20 帧静音上下文，C++ | 0.00000308 | 5.1200 秒 |
| 原频谱末尾补 20 帧静音上下文，PyTorch | 0.00000354 | 5.1200 秒 |

静音帧为 log(1e-5)，在波形还原**之前**补入；不是给输出 WAV 做淡出。C++ 补帧版本的前 4 秒波形逐点不变。增加到 40 帧后最后 20 ms RMS 仍约 0.00000310，没有获得新的语音内容。

用户听过 20 帧版本后确认：**仍然被掐断，比之前自然一些，像录音只录到这里；此前更像合成瑕疵。** 因此，波形还原的边界处理会加重异常，但补静音上下文没有解决完整尾音问题，不能作为最终修复上线。

### 参考音色与未解决项

同文本、同种子、同参数，仅换参考输入：官方音色样本末尾能量接近静音；迪丽热巴未经过清理的保留原音也产生明显末尾能量。因此，不能把问题单独归因于去伴奏处理。参考音色相关条件值得继续检查，但“最后能量低”不等同于用户听感自然，也不能直接证明参考音频就是根因。

这些实验确认了波形末端边界问题，也证明仅修波形边界不足以补齐音节。最终修复需为更早的声学生成模块提供上下文；不能把原版本中间与末尾异常强行归为同一原因。

## 采用的修复

Music Room 基于 audio.cpp v0.9.1 构建 `0.9.1-music-room-tail1`，仅对 IndexTTS 2.0 增加可选的声学收尾上下文：

1. GPT 生成的语音编码保持原值；声学条件末尾补 32 帧空白向量，原序列的初始噪声保持一致。
2. 声学生成使用扩展后的条件，波形还原前另补 20 帧 log(1e-5) 静音上下文。
3. 输出保留原长度后额外 12 帧自然尾音，去除多余保护段；最后 20 ms 余弦淡出，追加 100 ms 静音。不是直接在旧 WAV 上拉长或裁切。

同一固定输入的原生对照保持 GPT 编码完全一致；原长度边界处最后 20 ms RMS 从 0.078590 降至 0.001579。用户试听声学上下文对照后确认“结尾自然了，中间也正常”。这确认指定样本的效果，不承诺任何音色和任意文本都不会出现韵律异常。修复新增约 0.24 秒收尾时长；真实队列回归的 9 条音频均成功，四个音色、长文与取消恢复通过，物理峰值约 4.9 GiB；同参考短句约 18.97 秒，详细结果见当前引擎文档。

原生补丁、构建入口与固定包校验见 [构建说明](../native/audio-cpp/README.md)。模型仍为同一份 F16 GGUF，没有通过降低精度或提高候选数换取此次改善。

## 复现材料与后续可追踪性

诊断源码保存在 `scripts/diagnostics/tts-boundary/`：`capture-v0.9.1.patch` 仅向上游增加采集，`vocoder-probe.cpp` 重放频谱，两个 `replay-torch-*.py` 分别重放原版模块，`analyze-vocoder-boundary.py` 输出对照指标。

1. 用 `git apply --unidiff-zero` 将采集补丁应用到独立的 audio.cpp v0.9.1 源码副本，构建 IndexTTS2 CLI；不要修改正式安装目录。
2. 设置 `MUSIC_ROOM_DIAGNOSTIC_DIR` 为绝对目录，以种子 42、一路候选、上文文本和内置 `dilireba.wav` 运行。目录内保存编码、频谱以及 CFM 全部重放输入。
3. 用现有 IndexTTS2 Python 环境执行重放脚本。`MUSIC_ROOM_TTS_DIRECTORY` 可指定已有模型根目录，默认 `~/Music/IndexTTS2`；脚本离线加载已缓存的原模型。CFM 仅运行该模块，不加载完整 Python TTS。
4. 将 `vocoder-probe.cpp` 复制到诊断源码根目录，在 CMake 中另加 `add_executable(music_room_vocoder_probe vocoder-probe.cpp)` 并链接 `engine_runtime ggml`。探针参数依次为模型、频谱文件、帧数、补帧数、后端、输出 float32 文件。本例帧数 421、补帧 0 / 20 / 40、后端 metal。

本机详细结果位于 `test-results/audio-cpp-trial/diagnostic-seed42/`，包括 `boundary-analysis.json`、`eos-padding-check.json` 和 `torch-cfm-result.json`；原始音频和大型中间数据不提交仓库。实验前确认正式队列空闲，诊断进程结束后保留正式常驻引擎。

原失败版本没有保存随机种子，无法保证重新生成同一失败样本。现已补齐：新版本在入队前保存随机种子，驱动显式传递；API 支持指定原种子重放。68 项服务测试通过，正式独立服务连续生成两次（种子 4043328507），WAV SHA-256 完全相同，且复用同一引擎 PID。旧 22 个版本和 20 份音频保持不变。此结果仅证明当前引擎、模型、参考与参数下的本机重放，不保证跨设备或升级后逐字节一致。
