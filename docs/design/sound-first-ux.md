# Music Room：围绕声音创作的 UX 提案

状态：整体声音创作流程有可交互原型；普通语音已在正式 `/speech.html` 页面接通 IndexTTS 2.0，持久化项目、声音、版本和真实音频。音乐主工作台与 MIDI 加工仍沿用现有流程，尚未整体替换。
依据：2026-10-08 用户提供的创作故事与当前代码。没有其他用户访谈或可用性测试证据，易用性判断仍需实际操作验证。

原型：运行 `npm run dev` 后打开 [/prototypes/sound-first/index.html](http://127.0.0.1:5173/prototypes/sound-first/index.html)。

## 1. 产品应该让用户做什么

**创建项目，描述想要的声音，试听几个版本，留下喜欢的，继续修改或导出。**

默认工作区围绕声音和创作结果组织。波形、时间与试听服务于判断结果；MIDI、音符、小节、音轨、引擎安装属于按需进入的工具。

### 1.1 三个用户需要理解的概念

```text
项目：秋日短片
├── 声音：开场吉他 riff（音乐片段）
│   ├── V1：留作灵感
│   └── V2：选作成品
├── 声音：片尾曲（完整音乐，带人声）
│   ├── V1：初次尝试
│   └── V2：基于 V1 修改
└── 声音：片头旁白（语音）
    └── V1：选作成品
```

- **项目**收纳同一次创作所需的一个或多个声音，不等于一首歌。
- **声音**是用户要完成的对象，例如一个 riff、一首歌曲、一句旁白。音频、MIDI、分轨是它的文件或加工结果，不是三个互不相干的作品库。
- **版本**是对同一个声音的一次尝试。模型生成、Agent 创作和导入文件产生的结果都进入这里。

同一个项目可以有多个成品。每个声音默认选一个成品版本；需要两个独立交付对象时，创建两个声音。是否需要同一声音多选交付版本，待实际使用验证。

### 1.2 声音类型不是引擎分类

| 用户选择 | 主要填写内容 | 首屏不要求理解的内容 |
| --- | --- | --- |
| 音乐片段 | 描述、目标时长；需要时说明 riff、间奏等用途 | 小节、调号、音轨数量 |
| 完整音乐 | 纯音乐 / 带人声、描述、目标时长；带人声时提供歌词 | 模型安装目录、推理参数 |
| 语音 | 参考声音、朗读正文、可选情绪描述；使用 IndexTTS 2.0 | MIDI、配器、音乐段落 |

目标时长不是模型保证。正式界面必须区分“希望 3 分钟”与“实际 2:47”。

用户通过明确选项选择类型；Agent 可以结合上下文提出建议。不得用提示词是否包含某些词来偷偷切换声音类型、模型或创作流程。

## 2. 页面怎么组织

### 2.1 项目导航

左侧只放项目和“新建项目”。创建只要求名称，进入后直接显示“创建第一个声音”。不要求提前配置模型、音轨、BPM 或文件夹。

项目首部展示项目名和“项目成品”。下方是本项目的声音列表，名称下显示类型与版本数。切换声音不丢失已输入的描述。

原型用紧凑卡片展示少量声音；项目超过约六个声音时，应切换为可搜索列表，不能无限加高卡片区。具体阈值待使用验证。

### 2.2 声音工作区

桌面：左侧试听与版本，右侧创作要求。窄屏：单列，先试听与判断，再继续创作；空声音提供明确的创作入口。

用户始终能回答三个问题：

1. 我现在在做哪个声音？标题和类型可见。
2. 我现在听的是哪一版？播放器明确显示 V1 / V2，成品与灵感标记分开。
3. 接下来怎么做？修改这版、再生成一版、保留、选成品、下载。

播放器显示播放 / 暂停、时间、进度、循环。默认不展示钢琴卷帘、轨道矩阵、BPM 或小节选择。没有音频时说明原因，不画假波形、不播放其他版本冒充结果。

### 2.3 创作入口

首版填写“想要什么声音”。已有版本时，可直接再试，也可点“修改这版”：带上来源版本和原始要求，再补充希望改变的内容。

带人声歌曲将歌词单独展示；语音将朗读正文与声音要求分开。两种类型都保留自然语言描述，不要求用户先理解模型参数。

“生成模型”和“交给 Agent”是创作方式，不是两个作品管理系统：

- 模型：在当前声音中创建生成任务，完成后出现新版本。
- Agent：明确提供当前项目、声音、来源版本、要求及文件上下文；结果回到同一声音。
- 尚未接通 Agent 时，入口应明确叫“复制创作要求”，不能显示已提交或正在创作。

模型选择、质量等次要参数按需展开。没有兼容引擎时，在创作入口说明不可用原因并链接设置；不要让用户提交后才发现此引擎不能生成语音。

### 2.4 语音引擎：IndexTTS 2.0（已确定）

用户指定普通语音使用 **IndexTTS 2.0**，对应官方权重 `IndexTeam/IndexTTS-2`。实施时固定经过验证的代码提交与权重版本；不随上游默认分支切换到其他版本。

语音主流程：**添加参考声音 → 填写朗读正文 → 按需描述情绪 → 生成并试听新版本**。

- 参考音频决定音色；不能仅凭“女声、温暖”等描述承诺生成指定音色。正式产品应支持保存、复用参考声音。
- 情绪描述可选，留空时沿用参考声音的情绪；高级情绪参考音频和强度控制按需展开。
- 不显示精确时长或语速滑块。官方 2.0 发布说明标明时长控制尚未启用；不能把其他版本的语速参数作为 2.0 的能力。
- 版本保存朗读正文、参考音频的文件标识与哈希、情绪配置及引擎版本，确保后续修改有明确来源。
- 安装、硬件适配、模型准备和运行状态放在设置中；创作入口展示实际就绪状态。运行条件与性能在正式接入时验证，不预先承诺本机速度。

正式语音页面已接通上传、参考复用、情绪推理、多版本、比较、成品选择、删除恢复和真实 WAV 下载，见 [使用与运行环境](../tts.md)。参考和产物保存到工作目录，读取核对哈希；原型继续用于展示整体音乐流程，不承担正式语音生成。

依据：[官方仓库的 IndexTTS2 用法与发布说明](https://github.com/index-tts/index-tts)、[官方 2.0 模型](https://huggingface.co/IndexTeam/IndexTTS-2)，核对日期 2026-10-08。

## 3. 版本的操作规则

| 操作 | 用户看到的结果 |
| --- | --- |
| 生成新版本 | 新增 V3；V1、V2 和已选成品不变 |
| 基于这版修改 | 新版记录来源；原版保持不变 |
| 保留灵感 | 给该版本加星标，可筛选；不代表成品，也不影响其他版本 |
| 选作成品 | 当前声音的交付版本更新；旧成品仍保留为普通版本 |
| 比较 | 勾选两版，分别试听；一次只播放一个 |
| 删除 | 该版本进入回收站，可撤销；不删除后代版本 |
| 删除当前成品 | 清除该声音的成品选择，不自动拿另一版替代 |
| 恢复版本 | 恢复内容和灵感标记；不偷偷改回成品选择 |
| 删除最后一版 | 声音仍存在，显示可继续创作的空状态 |
| 下载 | 文件明确属于当前声音和版本；不会下载其他版本充数 |

普通比较不能要求两版速度、结构、长度一致。先支持独立试听，准确的段落对齐比较是额外能力。未做响度归一化或对齐时如实提示。

删除是可恢复的日常操作，不需要每次弹窗确认。正式服务的永久删除另外处理，需明确文件范围与引用关系；本原型没有永久删除入口。

### 3.1 生成状态跟着声音走

排队、运行、完成、失败、取消直接显示在对应版本位置，不要求用户去全局“后台任务”里找结果。

- 离开声音或项目，任务仍归属于原声音，完成通知带声音名与版本号。
- 正式服务重开页面后恢复后台真实状态；原型没有后台，刷新会将未完成的模拟任务标为中断。
- 失败保留创作要求，可以修改后重试。失败尝试不覆盖成功结果。
- 取消后的迟到结果不得重新激活任务。
- 提交后继续编辑，编辑的是下一次草稿，不能悄悄改变已提交要求。

## 4. MIDI 和音轨在什么位置

从当前版本的“继续加工”进入，结果保留来源关系：

```text
音频版本 → 分离音轨 → 单轨试听 / 下载 → 需要时转 MIDI
已有 MIDI → 乐器音源合成 → 音频版本
MIDI + 歌词 + 对齐信息 → 歌声合成模型 → 人声音频版本
文字 + 参考声音 + 可选情绪 → IndexTTS 2.0 → 语音版本
```

MIDI 本身不是语音，不包含完整音色或录制的人声。不能把“导入 MIDI”包装成已经具备 TTS 或歌声合成能力。

- 已有 MIDI：直接提供下载或展开详情，不要求重新识别。
- 只有音频：需要独立的分轨、转录能力，不承诺一键准确还原。
- MIDI 详情：轨道、音符、乐器按需展开，不是默认声音展示方式。
- 导入：明确选择“作为新声音”或“作为这个声音的新版本”，不能凭文件名推断归属。
- 加工结果：放在源版本附近，不挤占普通生成版本列表；成为独立创作目标时，可以另存为声音并保留来源。

原型展示已有 MIDI 下载与加工入口的能力边界。分轨、转录、歌声合成、TTS 没有伪造已完成状态。

## 5. 现有实现为什么难用

| 现有证据 | 对用户的影响 | 需要的调整 |
| --- | --- | --- |
| `src/workbench/app.ts` 默认展开整曲音符、局部小节和十一条音轨 | 听一个结果前先面对编曲工具 | 试听和版本优先，音乐细节按需展开 |
| `src/workbench/service.ts` 将创建项目放在“本地项目与 MCP”折叠区 | 最基本入口与技术设置混在一起 | 项目创建独立、常驻 |
| `src/workbench/yue2.ts` 按引擎展示全局任务和音频 | AI 结果与现有作品、乐谱版本分散 | 所有产物统一归属项目和声音 |
| `ProjectStore` 的 `Revision` 必须带 `scorePath`，项目直接包含版本 | 音频、语音和一项目多个声音不易自然表达 | 增加声音层；版本允许以音频或 MIDI 等素材起步 |
| `operations.ts` 没有版本删除或灵感 / 成品标记 | 本地服务缺少故事中明确要求的管理能力 | 补齐持久化操作和引用保护 |
| 现有 A/B 要求对应段落与相同长度、速度 | 很多正常生成版本无法比较 | 普通听评不依赖乐谱对齐 |

这不是只修改颜色和排版就能解决的问题。视觉改造必须和上述对象关系同步，否则用户仍需自己拼接几套功能。

## 6. 原型范围与落地顺序

### 6.1 本次可实际验证

项目创建、多声音切换、按类型创建、模拟多版本生成、失败与取消、来源版本、灵感标记、成品选择、回收站与撤销、双版本比较、真实示例音频播放、已有 MIDI 下载、文件导入、浏览器内状态恢复，以及桌面和窄屏布局。

原型数据独立保存在浏览器，既不是正式项目文件，也不会调用生成模型。导入文件仅在当前页面可用，刷新后需重新选择；不会把这一限制包装成持久文件管理。

### 6.2 正式实现的顺序

1. **对象与迁移**：项目新增声音层；版本支持音频或 MIDI 等源文件；旧项目迁移为一个声音，保留所有原文件与 ID 引用。
2. **主闭环**：项目创建、声音创建、类型表单、统一任务归属、试听、灵感、成品、可恢复删除；生成与 Agent 共用相同对象和写盘接口。
3. **结果加工**：先接已有 MIDI 与音源渲染，再逐项接入有实际引擎支持的分轨、转录、IndexTTS 2.0 语音、歌声合成。不可用能力保持清楚的状态。

第一步和第二步必须一起完成才能称为正式改版。新界面不应仅把旧的两套列表藏起来。

### 6.3 验收场景

- 首次进入，从空项目到第一条生成要求，不需要接触 MIDI、小节或安装路径。
- 同一项目放 riff、完整歌曲、旁白；各自版本不串位。
- 从 V1 修改得到 V2，同时保留 V1 为灵感；再生成 V3，已选成品不变。
- 生成途中切换声音，结果仍落到原声音；失败能找回要求，取消不会晚到复活。
- 删除有后代的版本，后代仍能播放；撤销恢复；刷新后管理状态仍存在。
- 不同长度的音频能独立比较；切换和关闭比较不发生双重播放。
- 不懂 MIDI 的人能完成“听、改、选、下载”；需要 MIDI 的人能从当前版本找到它。

交互检查只能证明这些操作按规则工作，不能代替真实用户对“顺不顺手”的判断。

### 6.4 本次验证

运行中的 Vite 服务用于浏览器验证：

```sh
node --test scripts/verify-sound-first-model.test.mjs
node scripts/verify-sound-first.mjs

```

结果：5 项原型状态测试、10 组浏览器交互检查、27 项现有单元测试与构建通过。浏览器覆盖真实音频播放、比较时单一声源、删除撤销、跨声音任务归属、失败重试与取消、创建流程、MIDI 导入、刷新恢复，以及 1440 / 1024 / 768 / 390 像素布局；没有捕获到页面脚本异常。
