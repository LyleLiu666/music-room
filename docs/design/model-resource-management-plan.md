# 模型服务与硬件资源管理开发计划

状态：待执行。本文只安排开发工作，所有阶段均未验收完成。
当前逐轮进展及入口核对见[开发记录](model-resource-development.md)；完成记录以其中的验证事实为准。

设计依据：[模型服务与硬件资源管理](model-resource-management.md)。产品规则、预算原则以设计文档为准；本文规定实施顺序、代码落点、测试和交付标准。实施中若发现设计不可行，先修订对应设计，不在代码里悄悄改变规则。

## 1. 交付目标

将 IndexTTS 2.0、YuE2、Seed-VC 及辅助音频处理纳入统一资源管理，做到：

- 同一用户在同一台电脑上最多执行一个重型任务；跨工作目录也不能绕过。
- 切换前确认旧模型退出，资源不足时不加载新模型。
- 按实际内存拓扑、容量、当前压力和任务需求分配预算；不写死 32 GiB，不把独立显存与系统内存相加。
- 下载、安装、加载、运行、卸载的状态明确；已有作品的播放和管理不依赖模型驻留。
- 取消、失败、服务退出后能回收所属资源，保留输入和已完成产物。

首轮实现当前已有的 macOS Apple Silicon 后端。独立显存、CPU 和其他平台通过契约及模拟测试覆盖预算逻辑；未完成平台适配和真机验证前显示不支持，不宣称已经能运行。8 / 16 / 24 / 32 / 64 GiB 是测试容量，不是预先承诺的模型支持清单。

本轮不增加模型并行、云端回退或自动降低精度。容量不足的设备仍应能使用作品管理和播放功能。

## 3. 开发约定

### 3.1 代码与接口边界

| 位置 | 计划职责 |
| --- | --- |
| `src/service/resources/`（新增） | 资源契约、准入策略、统一队列、账本、用户级租约、平台探测及就近测试 |
| [service.ts](../../src/service/service.ts) | 初始化唯一协调器，注入各业务服务；统一停止准入和退出顺序 |
| [tts/](../../src/service/tts/) | TTS 驻留状态、加载/卸载、参考清理、原生与 Python 路径接入 |
| [yue2/](../../src/service/yue2/) | 本地任务代理、内部任务映射、生成监管、离线历史和音频访问 |
| [conversion/](../../src/service/conversion/) | 整条转换流水线的预算、取消、阶段变化和进程树监管 |
| [jobs/jobs.ts](../../src/service/jobs/jobs.ts)、[studio/](../../src/service/studio/) | 乐谱渲染、调速任务、业务记录及状态投影 |
| [operations.ts](../../src/service/operations.ts)、[server/](../../src/server/) | 统一查询与操作契约、HTTP/MCP 一致性 |
| [workbench/studio/](../../src/workbench/studio/) | 设置页资源状态、任务等待与取消、创作入口就绪判断 |

不预先拆出大量单方法文件，不创建通用调度框架。共享语义稳定的资源管理能力集中管理，各引擎专有逻辑与其测试留在引擎目录。

### 3.2 必须固定的契约

- 硬件快照包含资源池关系、容量、可用估计、压力、交换空间变化、数据时间和可信度；未知值不是 0。
- 任务需求区分整个任务峰值、当前驻留占用、尚未分配的预约和本次增量，禁止重复扣减。
- 适配器提供需求估计、执行、取消、驻留查询、卸载与确认退出的能力。所有加载动作由已获准的执行上下文触发。
- 协调器不保存第二份作品库。各业务服务持有稳定任务 ID、输入和结果，协调器持有执行权与资源状态。
- 排队时只保留必要输入引用。提交返回不能等待资源获取，不能提前解码整首音频。
- 状态按设计文档映射到现有业务状态；第一版优先增加统一的资源子状态与原因码，保留旧任务顶层枚举的兼容映射。等待/加载映射为旧接口的排队或运行，阻止执行映射为失败并保留原因，不能让旧客户端永久轮询。
- 同一流水线持有一个执行权；人声分离再转换等内部阶段复用它，不再次排队申请，避免自锁。

### 3.3 TDD 与证据

每项任务先增加可观察行为的失败用例，确认它因目标缺口失败，再实现并重构。新增模块尚不存在时的导入报错不是唯一红灯证据；补最小契约后，测试应能证明调度、预算或退出行为不满足。

调度测试用可控时钟、硬件快照和进程门闩，避免靠固定等待猜测先后顺序。进程监管必须启动受控子进程验证实际退出。真实模型验收单独运行，普通自动测试不得下载权重或加载真实模型。

## 4. 分阶段任务

### P0：确认入口、状态与现有回归

**改动与产物**

1. 列出网页、HTTP 上传、MCP、业务服务直接调用、自动启动、安装脚本及引擎内部队列的全部加载与执行入口，逐项指定由哪个适配器接管。
2. 核对 YuE2 上游固定版本的加载时机、预取、任务恢复、停止和历史读取行为；记录证据位置。不能凭“HTTP 服务启动成功”推断模型未驻留。
3. 明确 YuE2 本地任务 ID 与上游 ID 的映射、历史迁移和停止后读取方式。当前 ID 校验要求 32 位十六进制，迁移不能随意改格式。
4. 明确新增资源子状态与现有 TTS、转换、YuE2、Studio、渲染任务状态的映射，以及删除保护对所有非终态的处理。
5. 执行 `npm run test:service`、`npm test` 和 `npm run build`，记录当前基线；已有故障单独登记，不混入本次完成记录。

**先写的测试**：TTS 驻留后启动转换；YuE2 与 TTS 同时提交；卸载 YuE2 后读取已完成音乐。现有三项互斥测试保留其保护意图，后续将“拒绝新语音”调整为设计要求的“安全排队”。

**完成标准**：上面三条缺口有行为复现；调用清单覆盖三引擎、辅助处理、自动启动和安装；P3 的任务代理方案无待定的身份或状态冲突。

### P1：统一队列、账本与准入

**改动**：在 `src/service/resources/` 实现纯预算判断与协调器；在 MusicService 中创建并注入。硬件探测、时钟和适配器均可注入，测试不依赖开发机容量。

1. 实现有界 FIFO 队列，统一入队序号和取消；各引擎原队列保留记录能力，不再单独选择执行时机。
2. 区分永久容量不足、临时资源不足、设备不支持、需求未知、探测失效；准入返回结构化原因。
3. 实现先卸载、再采样、原子预约、执行、清理与驻留转账。卸载未确认时不得释放执行权。
4. 同模型连续任务可复用已确认驻留的进程，但仍检查增量需求及整机压力；异模型切换必须卸载。
5. 临时资源不足时等待且可取消；等待超时转为可重试的阻止状态，让后续任务获得评估机会。
6. 队列满或重复请求不能留下孤立业务记录；持久化失败必须撤销预约，不能启动工作进程。

**先写的测试**：三任务竞争只有一个执行；取消与获准同时发生；卸载失败；重复完成不重复释放；驻留量不归零；排队时没有音频读取；队首超时；不同容量与独立显存组合；加载前快照变化；需求或指标缺失。

**完成标准**：全部场景通过，预算无负值、重复扣减或泄漏；调度逻辑没有读取固定开发机数值。

### P2：跨实例租约与进程监管

**改动**：在用户级应用状态目录实现原子租约，路径由平台适配确定；复用项目现有 stdin 生命周期监管经验，补齐所有引擎的终止升级和进程树确认。

1. 租约绑定实例身份、随机拥有者标识及可验证的进程身份；不能只依赖 PID，必须处理 PID 重用。
2. 获准加载前拿到租约；活动任务或空闲模型仍占资源时不得释放。等待本机其他软件释放内存时，先卸载本实例模型，再释放租约，避免空占执行权。
3. 进程组归属与后代存活检查覆盖优雅退出、超时强制退出、父进程异常退出及恢复。无法确认归属时阻止加载并提示诊断，不猜测杀进程。
4. 验证跨实例持有租约的顺序：本实例已有驻留模型时必须识别自己持有的租约，不能等自己释放后才开始卸载。
5. 第一版只保证实例内 FIFO；跨实例不承诺全局 FIFO。持有者收到其他实例的等待请求后，完成当前任务、卸载模型并交还机会，不能因连续任务或空闲驻留永久占用。具体交接机制在本阶段用多进程测试定稿；心跳或等待超时只能触发归属检查，不能在旧进程仍占资源时强行授予新租约。

**先写的测试**：两个工作目录同时争抢；主进程被终止但后代仍活着；PID 重用；损坏租约；卸载超时；无关进程不受影响；连续任务下另一实例最终可获得执行权。

**完成标准**：用真实受控子进程证明最多一个拥有者、取消后无所属进程残留、损坏或不明状态不放行；租约目录权限和原子写入通过检查。

### P3：接入三个主引擎

| 工作包 | 具体改动 | 必须先失败的集成用例 |
| --- | --- | --- |
| P3.1 TTS | 为原生 driver 增加明确卸载与驻留信息；区分可复用卸载与永久关闭；Python 路径也由同一协调器管理 | 已生成语音仍驻留时，转换必须等待 TTS 真实退出；取消加载后不能迟到启动 |
| P3.2 转换 | 整个分离、换声、升降调和混音流水线共用一次执行权；把固定 10 GiB 规则替换为协调器下发的有效额度 | 分离与后处理仍计入占用；取消后全部所属进程退出；不能因下一阶段重新申请而死锁 |
| P3.3 YuE2 | 提交先保存本地任务，获准后才发给上游；后台轮询直到真实终态；接管自动启动和上游队列恢复 | HTTP 返回任务 ID 后仍占执行权；网页关闭后继续执行；旧队列不能在重启时自行加载 |
| P3.4 统一接线 | 删除两两 busy 回调决策，所有生成入口使用同一调度；退出先关闭准入再回收引擎 | direct TTS、Studio、MCP、转换上传与 YuE2 互相竞争时均不会绕过 |

**YuE2 专项要求**

- 本地任务代理维持稳定的用户可见 ID，保存上游 ID 映射；已有历史 ID 与已有版本引用继续有效。上游尚未提交时也能查询、取消和重试本地任务。
- 上游请求结果不明确时先按可验证标识核对，不能盲目再次提交造成两份生成。无法核对则记录中断原因，等待显式重试。
- 历史与音频读取改为本地记录及受路径/归属检查的文件访问，或证明确实不会加载模型的独立轻量入口。首选本地读取；不可通过重启推理后台恢复播放。
- Studio 当前同步依赖 `canGenerate`，需改为独立读取任务与历史；客户端“可以提交”不能再等同于“模型已加载”。
- YuE2 内部会触发模型的直接接口必须受拥有者执行权约束，不能保留绕过主服务的启动或预取路径。

**完成标准**：三个引擎的所有方向切换均经过卸载确认；状态刷新不加载模型；服务重启不自动执行历史重型任务；原语音、转换、音乐产物与项目归属测试继续通过。

### P4：关闭辅助处理与安装的遗漏路径

**工作包**

1. **参考人声清理**：准备环境、加载辅助模型、去噪和去混响统一入队；仅保存原始参考音频不触发推理。
2. **乐谱渲染**：接入 JobManager 与渲染子进程；已有提交幂等、取消、音频提交校验继续成立。大型结果的父子进程传输与写盘峰值进入估计。
3. **调速**：将整段解码和处理移入受监管工作进程，以文件引用传递输入/输出，防止父进程复制大缓冲区。保存调速版改为可查询、可取消的后台任务；现有操作返回对应排队版本，更新调用方和兼容说明。
4. **安装**：TTS、YuE2 和转换模型的已有下载、解压、转换、校验能力采用统一安装任务，与重型推理互斥；将转换安装脚本可复用步骤接入服务，脚本不得成为独立无预算旁路。当前转换安装脚本接收本地程序和权重文件，首轮保留这种来源并统一管理；若要增加自动下载，必须先确定可发布的安装包、来源与校验清单，不假定已有下载能力。
5. **磁盘管理**：检查下载、解压和最终文件所在卷的空间及峰值，跨卷分别计算；测试续传有效性、服务端不支持续传、校验失败、取消、并发删除保护及缓存清理。
6. **常驻内存边界**：限制待处理上传和任务队列的字节规模；客户端音频缓存随使用回收，关闭不再使用的 Blob URL，避免连续试听形成无界缓存。播放仍保持独立响应。

**关键约束**：等待资源或计算完成时不得占住 Studio 的业务串行锁，否则查询、取消、删除检查可能全部堵住。只在保存输入与提交最终结果时进入短事务；结果发布期间明确取消边界，不能出现“已取消但又发布成功”。

**先写的测试**：三个模型任务与调速/渲染/清理交错；调速排队时仍能查询并取消；0.5 倍调速输出内存估计；长音频后处理；安装与推理竞争；磁盘被外部写满；取消时没有成品半文件；播放器缓存回收后仍可重新播放。

**完成标准**：不存在已知高负载旁路；任务输入和历史成品保持完整，原来的时长、立体声、升降调和音频有效性回归继续通过。

### P5：平台探测、监控与真实需求档案

**改动与测量**

1. 实现 macOS 内存拓扑、容量、压力、可用估计、交换空间变化及本应用进程树占用采集；记录指标口径、采样时间与无法测量的项，统一内存避免重复相加。
2. 统一配置停止、恢复、监控失联和卸载超时策略。后端自身限制由任务获准额度推导；不能仍让 YuE2 或转换分别决定全机预算。
3. 在固定版本与输入下测量各引擎冷加载、驻留、推理、阶段切换、最长允许输入、取消和卸载；参考处理与长音频混音独立记录峰值。
4. 建立随发布打包的需求档案，包含模型/程序校验标识、精度、后端、输入范围、测量证据和可信度。只启用有有效档案的配置；升级不自动沿用失配档案。
5. 用不同容量真机确定系统预留、动态余量、采样频率和停止阈值。先有带保护的测量工具，再加载真实模型；测量模式只存在于开发验证脚本，不暴露给普通生成接口。
6. 将定稿数值写回设计文档及集中配置，记录证据；对未拿到硬件的配置保留“未验证”，不为了过验收制造测量数据。

**先写的测试**：采样命令超时和格式异常；过期快照；共享页重复计算；进程退出时采样回调迟到；压力在阈值附近波动；持续超额及立即超额；档案缺失或版本失配；用户收紧额度后重新评估队列。

**完成标准**：自动策略测试通过，当前拟支持配置有真实测量与保守额度；运行时保护能停止受控任务且不自动重试。采样监控与硬分配上限在说明中明确区分。

### P6：统一接口、页面与迁移

**改动**

1. 在 operations 和 OperationResults 中增加资源状态、资源策略设置及释放空闲模型操作；名称与输入模式在本阶段固定，HTTP/MCP 使用同一实现。预算只能收紧，调整后的校验和生效时机必须可测试。
2. 资源快照包含硬件、预算、当前任务、队列、等待原因和各模型安装/运行状态。敏感路径与原文不写入通用诊断日志。
3. 设置页改为「本机模型与资源」，显示真实检测数据；创作表单按“可提交/需安装/不支持/容量不足”判断，模型未加载不再阻止正常入队。
4. 提供取消排队、取消执行与释放空闲模型。活动任务期间释放操作返回忙碌并引导取消，不隐式取消用户任务。
5. 迁移旧 YuE2 自动启动设置与状态文案；更新操作描述。旧启动接口保留结构兼容，但不能承诺立即进入 running，更不能绕过预算。
6. 旧业务数据不需要推理即可迁移；迁移前保存可恢复副本，失败保持原数据可读。升级中断不重复创建版本或重跑任务。

**先写的测试**：HTTP/MCP 两端相同原因码；资源等待时界面仍可操作；刷新与重开显示同一任务；指标未知显示未知；预算输入越界；安装成功仍未加载；卸载音乐后历史播放；旧 autoStart 配置启动服务不加载模型；窄屏和键盘操作。

**完成标准**：正式首页、旧入口、MCP 与状态查询一致；原有项目、版本、回收站及下载回归通过；用户能知道正在等什么并能取消。

### P7：综合验证与交付

1. 执行下节验证矩阵，逐项保存结果，失败修复后重跑受影响检查。
2. 使用隔离工作目录验收；不改用户模型配置，不覆盖真实作品，不通过同时加载三个大模型来“测试会不会卡死”。
3. 按已支持硬件收集真实峰值、交换空间变化、前台交互响应、释放耗时和音频产物校验。压力实验达到预设停止阈值就结束。
4. 构建独立二进制并从干净目录运行，验证新增平台探测、子进程入口、需求档案和前端资源确实被打包。
5. 更新本地服务、三个引擎使用说明与设计状态；填写阶段结果和限制。保留“实现完成”和“某硬件实测通过”的区别。

**完成标准**：所有入口受统一调度，模型卸载有进程与内存证据，支持范围有真机依据，旧作品可用。缺少低容量或独立显存真机时，明确收窄支持范围，不能以模拟测试填补该项验收。

## 5. 验证矩阵与执行命令

| 层级 | 范围 | 执行方式 |
| --- | --- | --- |
| 策略单元测试 | 不同容量/拓扑、预算账本、FIFO、取消竞态 | 新增就近 `*.test.ts`，纳入 `npm run test:service` |
| 进程与服务集成 | 多实例、生命周期、三引擎、辅助任务、状态持久化 | `npm run test:service`，新增 resources 和 server 用例 |
| 普通回归与构建 | 共享音频逻辑、类型与打包前检查 | `npm test`、`npm run build` |
| 服务边界与 MCP | HTTP/MCP 契约、归属与文件访问 | `npm run verify:service` 及 server 集成用例 |
| 页面回归 | 模型状态、排队/取消、历史播放、调速与转换 | `npm run verify:studio`；新增资源页用例接入该入口 |
| 真实资源验收 | 三模型峰值、释放、压力停止、连续工作 | 拟新增 `npm run verify:resources:real`，显式选取硬件和配置 |
| 原引擎音频回归 | 实际生成与原有音频规则 | 按改动运行 `npm run verify:tts:real`、`npm run verify:yue2:real`，并补转换的统一真实验收入口 |
| 独立发布产物 | 非源码目录启动及新增运行时资产 | `npm run build:binary`、`npm run verify:binary` |

新增命令必须在对应阶段实际写入 `package.json` 后才可标为已执行。检查测试发现规则确实包含新增文件；不能写了测试却没有进入常规命令。真实验收脚本先检查依赖、档案和磁盘，缺失时明确报“未执行”，不当成通过。

证据输出到忽略提交的 `test-results/resources/`，按验收批次隔离。报告记录提交版本、操作系统、硬件容量/拓扑、引擎与模型版本、配置、输入范围、峰值、终止与卸载事实、产物校验和测试结论。可长期复用的已验证摘要写入版本化需求档案，原始音频与日志不自动进入仓库。

## 6. 阶段完成记录与发布门槛

实施时在每阶段补充：完成提交、测试命令与结果、证据路径、未通过项及其影响。未拿到证据的项目保持未完成；不得把历史 TTS 的单机峰值直接当作本轮全配置需求档案。

- [ ] P0 调用清单、ID 与状态兼容方案完成，基线已记录。
- [ ] P1 统一调度与预算策略通过自动测试。
- [ ] P2 多实例和真实子进程回收通过验证。
- [ ] P3 三引擎所有生成、自动启动和内部队列路径已接管。
- [ ] P4 清理、渲染、调速、安装和大音频缓冲区无遗漏。
- [ ] P5 已支持配置有需求档案，数值策略已定稿并验证。
- [ ] P6 页面、HTTP/MCP、旧状态和数据迁移通过验证。
- [ ] P7 真实硬件矩阵、回归和独立二进制验证完成。

**整体验收前的阻断项**：YuE2 无法可靠停止或无法阻止内部自动运行；旧模型退出无法确认；预算探测失效却仍放行；主进程存在未计入的大缓冲区；模型配置缺少可信需求档案。遇到这些问题先修复或缩小支持范围，不用“默认串行”替代资源安全交付。
