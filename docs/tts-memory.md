# IndexTTS 2.0 内存诊断

2026-10-09，在 32 GiB Apple Silicon Mac、PyTorch 2.8.0、固定的 IndexTTS 2.0 程序与权重上验证。

## 当前内置音色结果

低内存路径已完成一条 108 字中文长文，输出 27.93 秒 PCM WAV。采样及进程自身峰值记录约 **9.5 GiB**，加载完成活跃 MPS 张量约 **3.92 GiB**。生成入口与正式服务相同，7 段在同一进程完成，耗时约 160 秒，不含加载；记录为 `preset-prefix6-long.log`、`preset-prefix6-long-samples.json`。随机生成的音频长度不同，不能据此宣称固定速度提升。

这是 32 GiB 本机上的指定输入实验，**尚未在实际 16 GB 硬件验收**，也不是任意输入的整个进程硬上限。自定义参考音色仍用原完整模型路径，不适用这组低内存结果。

正式后台驱动的隔离工作目录验收连续排队生成四条短句，同时仅一条运行，全部成功发布有效 PCM WAV，音频哈希与版本一致：

| 内置音色 | TTS 进程峰值 | 输出时长 |
| --- | --- | --- |
| 迪丽热巴（平静、温暖） | 9.0 GiB | 4.42 秒 |
| 天津团团记 | 8.8 GiB | 4.17 秒 |
| 女网红 | 7.5 GiB | 3.89 秒 |

记录为 `real-presets-result.json`，未修改用户项目库；旧 14 个版本、声音与所有已保存音频哈希已核对保留。页面五项交互测试、服务 60 项测试、普通单元 27 项测试、服务/浏览器 19 项检查及独立二进制验收通过。试听质量仍需用户验收。

## 短句断句修复

40-token 的统一限制引入了可复现的听感问题。用户“测试 2”的 V1/V2 文案经固定上游 BPE 编码分别为 49/50 个 token，却都被拆成两次独立生成；上游在片段之间插入固定 200 毫秒全零静音。旧 V2 的接缝位于 2.2291–2.4291 秒，接缝前 20 毫秒 RMS 约 0.101，声音仍明显存在，随后直接切入静音。旧 V1 也有相同结构。这说明先前只验证有效 WAV 和内存，没有覆盖自然断句质量。

当前修复让不超过 60 个 token 的短文连续生成，保留模型自身的停顿处理。更长文本保留已测的 40-token 分段预算；108 字长文仍为 7 段，没有扩大长文内存预算。这项修复针对短句被过度切分的缺陷，不能宣称长文所有接缝或任意听感问题都已解决。

使用两版原文、原内置音色及原情绪，V1/V2 都完成一次连续生成，分别输出 5.67/6.19 秒 PCM WAV，采样进程峰值约 9.2/9.3 GiB；两条新音频均未检测到超过 100 毫秒的全零区间。记录为 `pause-tokenizer.json`、`pause-result.json`、`pause-continuous-v1/v2.log` 及对应采样文件。真实波形与生成段数确认人工拼接接缝已消除，最终听感仍需人工试听。

回归测试先在旧实现上失败，再验证两条真实文案、60/61-token 边界及长文本的生成预算；自定义参考路径保持原上限。服务 61 项测试、构建与独立二进制验收通过。

## 原完整模型的诊断

模型加载完成时的进程内存负担约 **10.5 GiB**，其中 MPS 活跃张量约 **7.78 GiB**。之前观察到的 **42.4 GiB** 是生成阶段的整个进程内存负担，包含图形内存、压缩和换出的部分，不能当作模型权重大小或常规容量需求。

已确认两个可直接修复的因素，以及一项影响常驻方案的框架行为：

1. **GPU 缓存回收阈值过高。** 本机 Metal 推荐工作集为 24.96 GiB，PyTorch 默认软阈值换算成约 34.94 GiB，已经大于整机 32 GiB 的物理内存，尚未计入普通内存和其他程序。原配置下，同一段 108 字中文的生成过程中，活跃张量保持在约 9 GiB，MPS 驱动占用却增长到约 25.7 GiB。对照进程达到约 28.8 GiB 时主动停止；它尚未生成完整音频。原始用户任务的更高峰值为 42.4 GiB。这些观测说明高占用不能归因于权重本身。
2. **参考音频处理保留了不需要的训练数据。** 上游只在部分合成流程禁用梯度，参考声音的 style 与 prompt 处理仍会构建并缓存反向计算所需的数据。将整个 `tts.infer` 放进 `torch.no_grad()` 后，连续生成结束时的活跃张量由约 8.9 降到 8.0 GiB，参考缓存也不再带梯度或反向计算图。
3. **动态形状会增加 MPS 后端的缓存占用。** 在纯 PyTorch 注意力计算中，使用与 GPT 解码相同的非连续张量布局，连续执行 401 次；序列长度固定为 300 时，进程约 236 MiB、普通小块分配约 92 MiB。每步将长度从 100 增至 500 时，活跃 GPU 张量只有约 11 MiB，进程峰值仍达到约 1.8 GiB；`empty_cache()` 后普通小块分配还约 455 MiB。该增长可以脱离 TTS 模型复现，源于后端处理不同形状的行为。GPT 解码时序列长度逐步增长，长文本与不同生成长度也会产生新形状。

连续短文本生成时，即使执行垃圾回收、MPS 同步和 `empty_cache()`，清理后的进程占用仍会上升，不能保证模型常驻后一直维持 10 GiB。PyTorch 本地 MPSGraph 缓存实现保留按键索引的计算图。最小复现证明了后端的动态形状增长，但目前没有逐个分配追踪证明 42.4 GiB 中每一块额外内存都来自同一种缓存，也不能将所有增长直接称为泄漏。

## 当前修复

- 在受管理的语音进程中固定 `PYTORCH_MPS_LOW_WATERMARK_RATIO=0.5`，提前尝试回收缓存。
- 原完整模型固定 `PYTORCH_MPS_HIGH_WATERMARK_RATIO=1.0`，将 GPU 分配硬上限设为 Metal 推荐工作集大小；内置音色另按后文设定 7 GiB 预算。
- 整个第三方语音生成调用禁用训练梯度，包括参考音频处理。

这些比例控制的是 MPS 分配，**不是整个进程的 GiB 上限**。普通内存与框架开销仍需单独计量。上限达到时分配可能失败；这些设置不能让超出硬件容量的任务自动成功。

服务已在用户授权后重启，旧版本与音频保留。语音任务目前仍每次启动独立计算进程，避免常驻后的 CPU 图缓存累计；内置参考特征可跨任务复用。

PyTorch 2.8 的统一内存默认软阈值为 1.4、硬阈值为 1.7，均相对于设备推荐工作集。软阈值触发尝试回收与更频繁的提交；硬阈值限制分配。[官方说明](https://docs.pytorch.org/docs/2.8/mps_environment_variables.html)

## 实测与验证

### 正式后台任务

一条 45 字的实际用户任务已确认使用软阈值 0.5、硬阈值 1.0，生成阶段采样到的进程峰值为 **19.6 GiB**，成功输出 8.36 秒音频，保存文件与版本清单的 SHA-256 一致。这条任务运行时尚未加入整个调用的 `no_grad` 修复。

### 同一份模型连续生成三条短语音

独立诊断进程只加载一次模型，使用同一段 19 字中文、同一份约 15 秒参考音频和同一情绪。每条结束后执行垃圾回收、MPS 同步和缓存清理。不会写入用户版本库。

| 配置 | 加载完成 | 第 1 / 2 / 3 条清理后 | 三条总峰值 |
| --- | --- | --- | --- |
| 缓存阈值修复 | 10.5 GiB | 14.7 / 15.3 / 14.8 GiB | 20.1 GiB |
| 缓存阈值修复 + 整体 no_grad | 10.5 GiB | 13.6 / 14.5 / 14.9 GiB | 19.3 GiB |

六条音频都成功生成并通过 WAV 格式、时长与非静音检查。生成具有随机性，两组音频时长不同；该对照不能用于宣称固定的速度提升或完全相同的音质。只有三次短文本，不能推断任意时长、音色变化或长时间连续使用时的内存稳定性。

### 完整长文本

使用两个正式修复、同一段原始 108 字中文、同一份约 15 秒参考音频及情绪，按正式 Python 生成入口完成两段合成。输出 **24.50 秒**的有效 PCM WAV，采样到的进程峰值为 **19.6 GiB**；完成时活跃 MPS 张量约 **7.99 GiB**、驱动占用约 **14.37 GiB**。模型只加载一次，生成约耗时 181.5 秒；没有与用户生成任务并行。

该结果覆盖一次指定的长文本，不能视为所有输入的硬上限。原始生成具有随机性，与之前音频不逐样本相同；未进行人工听感评价。

原始诊断记录保存在本机 `test-results/tts-memory/`：`production-counters.log`、`warm.log`、`warm-nograd.log`、`fixed-long.log`、`actual-fixed-job.json` 及各自的采样、音频文件。框架最小复现为 `attention.py`，对应 `attention-strided.log` 与 `attention-strided-fixed.log`。该目录是临时验证输出，不随源码发布。

### 回归检查

先验证缓存阈值与整个调用禁用梯度的测试失败，再实施修复。语音回归还验证多条提交按顺序执行、同时只有一条生成，以及取消和音频保存。

`npm run test:service`：61 项通过（包含短句断句回归）。`npm run build`：通过。真实音频格式验证不替代人工听感验收。

## 队列与常驻模型

当前语音端已经串行排队，但每条任务重新加载并退出模型进程。音乐由另一个引擎管理，当前两类任务没有统一的内存调度。因此，“加队列”与“让模型常驻”是两项不同的改动。

后续常驻方案应具备：

1. 统一调度语音与音乐的重计算任务，避免各自串行、彼此却并发占满内存。
2. 同类连续任务复用一份模型；每条结束后回收临时数据。
3. 分别记录加载、生成峰值和清理后的占用。清理后超过预算时，在下一条开始前回收计算进程，防止累积增长。
4. 切换模型时执行明确的内存交接；是否同时常驻必须依据两者的联合实测。

目前只做了常驻对照实验，**尚未将常驻进程或语音与音乐统一队列投入正式服务**。TTS 与音乐模型同时加载的本机总占用也尚未实测，不能用之前的 42 GiB 异常峰值相加来估算。

## 16 GB 目标的内置音色优化

四个内置音色附带按固定原版 CPU 路径编码的特征，包含完整的声纹、风格、参考情绪和合成提示；哈希与原音绑定。生成跳过 W2V-BERT，不按名称选缓存。Mac 使用半精度 GPT，S2Mel 与 BigVGAN 保留原精度及 25 步扩散。情绪描述先由 Qwen 完整语义分析，结束后释放；无描述不加载它。没有用输入词表覆盖模型判断。

Mac 内置音色先按原版 BPE 计数：不超过 60 个 token 的短文一次连续生成，更长的文本仍使用最多 40 个 token 的片段，并在解码与阶段边界回收缓存。声纹与风格仍来自完整参考；波形合成阶段只使用最多 6 秒的对齐参考 mel/content 提示。原音和完整特征仍保留。该变化需由用户试听验收音色，WAV 检查不能代替听感。

额外设定 7 GiB 的 MPS 分配预算；它不能限制 CPU 图缓存或整个进程的总占用。之前尝试 6 GiB，以及未缩短合成参考的 7 GiB，都在长文合成中因分配不足失败，未将失败配置作为交付结果。真实验证记录见本机 `test-results/tts-memory/`。

## 替代内核与崩溃边界

[后端调研](tts-backends.md)覆盖原生 C++ 和 ONNX。当前未切换正式模型。

隔离的 MLX IndexTTS 2.0 移植能单次生成有效音频，短句峰值约 5.9 GiB，但重复生成仍出现 SIGSEGV/SIGBUS。Metal 验证已定位一处 FP32 注意力内核申请 35,840 字节线程组内存，超过本机 32,768 字节限制；转为半精度注意力可避开此验证失败，仍不能消除另一类崩溃。同步、版本与分阶段对照尚未证明剩余崩溃的完整原因，因此没有启用该实验后端，不能宣称崩溃已彻底修复，也不能归咎于 Python 语言。
