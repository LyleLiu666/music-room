# 模型服务与硬件资源管理

状态：待实现的设计。本文是三个生成引擎共享资源策略的设计依据，不表示现有程序已经具备这些保护。

实施步骤、代码落点与阶段验收见[开发计划](model-resource-management-plan.md)。

## 1. 目标与边界

IndexTTS 2.0、YuE2、Seed-VC 由 Music Room 本地服务统一管理安装、任务调度、模型加载、卸载和资源预算。用户可以安装三个模型，但程序不能因此同时把它们加载进内存。

核心目标是让用户生成声音时仍能正常使用电脑。资源不足时，应等待、拒绝启动或安全终止任务，保留输入和已完成作品。软件不能承诺在其他程序突然大量占用资源、驱动失效等情况下绝不卡顿；验收必须证明本服务的资源保护实际生效。

硬件能力必须在用户的电脑上探测。**不以 32 GiB、Apple Silicon 或统一内存作为所有用户的默认条件，也不承诺所有电脑都能运行三个模型。** 当前交付仍以 macOS Apple Silicon 为已验证平台；其他硬件的预算模型在本设计中明确，但只有实现适配并通过真机验证后才能声明支持。

### 1.1 确定的产品规则

- 一个后台入口管理三个引擎，网页、MCP 和内部工作流采用相同的准入规则。
- 第一版同一用户、同一台电脑一次只执行一个重型音频任务，包括模型加载、推理、参考人声清理、人声分离及高内存后处理。
- 切换引擎前释放旧模型，确认释放成功后才准许加载新模型。
- 下载完成仅表示文件已安装；不会自动加载模型或开始生成。
- 能否开始取决于当前可用资源和本次任务需求，而不是只检查物理内存总量。
- 播放、浏览、保存草稿和管理已有作品不等待模型队列；播放占用仍计入整机压力。
- 用户无需自行选择三个进程的内存额度。默认自动管理，高级设置只允许收紧应用预算。

### 1.2 范围

包含三个主引擎及其辅助模型、运行时、加载临时副本、音频解码和混音缓冲区、下载解压临时文件。乐谱渲染、调速等本地高负载任务也必须进入相同预算体系，防止模型被管住而后处理挤爆内存。

不在第一版提供模型并行推理、跨机器调度、自动切换云端、自动替换低质量模型或未经验证的 CPU 回退。不同模型可以复用同一安装根目录下的独立子目录，既有安装路径继续保留；统一管理不要求搬迁权重或混用运行环境。

## 3. 用户可见行为

### 3.1 设置页

将现有模型区域整理为「本机模型与资源」。顶部展示检测到的内存类型、总量、当前压力、应用预算和当前任务。统一内存只显示一个共享池；独立显卡分别显示系统内存和显存。读不到的数据明确显示“暂时无法读取”，不显示 0 或虚构可用额度。

每个模型分别显示两种状态：

| 维度 | 状态 |
| --- | --- |
| 安装 | 未安装、下载中、校验中、已安装、文件损坏 |
| 运行 | 未加载、等待资源、加载中、使用中、空闲驻留、释放中、失败 |

“已安装”不表示正在占用推理内存；“服务已启动”不表示模型可以在当前资源下运行。用户可以直接提交生成，由后台完成检查与加载，不需要先手动启动三个模型。

提供取消排队、取消当前任务、释放空闲模型内存和查看诊断。运行中点击释放内存时，应明确需要取消当前任务；不能悄悄中断生成。删除模型文件是独立操作，不等于卸载内存中的模型。

### 3.2 资源不足

| 情况 | 行为 |
| --- | --- |
| 其他 Music Room 任务正在运行 | 排队，显示当前任务及等待原因 |
| 本机理论容量够，但其他软件占用较多 | 等待资源，提示关闭占内存的软件；允许取消 |
| 单个模型的已验证最低需求超过本机容量或预算 | 在加载前阻止启动，说明具体资源缺口；不无限排队 |
| 任务更长，预计峰值超出预算 | 解释长度影响；仅提供引擎确实支持并验证过的分段或低内存选项 |
| 当前后端不支持这台设备 | 显示不支持及受影响功能，已有作品仍可使用 |
| 硬件信息或模型需求无法可靠确定 | 标记“尚未验证”，不自动试加载大模型；允许安装和管理作品 |
| 运行中达到危险压力 | 停止任务并释放所属进程，保存输入与失败原因，等待用户重试 |

重试必须重新检查资源。不得通过自动反复重启模型，把电脑持续推入内存压力。

## 4. 硬件探测与预算

### 4.1 资源池

| 硬件类型 | 预算规则 |
| --- | --- |
| 统一内存 | CPU 与 GPU 共用系统内存池，不能将“内存 + 显存”相加；后端工作集限制是附加约束 |
| 独立显存 | 分别检查系统内存和目标 GPU 显存；两者都满足才启动，上传模型时的主机临时副本计入系统内存 |
| CPU 后端 | 仅在该引擎已有受支持、经过验证的 CPU 实现时启用；检查系统内存和 CPU 并发限制 |
| 共享显存或无法可靠识别 | 按平台适配器的实际共享关系记账；无法确认时不按独立显存扩充容量 |

第一版每个任务只选择一个已验证设备；多 GPU 的显存不直接相加。交换空间不作为可分配模型内存使用。

探测结果包含：操作系统与架构、内存拓扑、物理容量、可用内存估计、压力等级、交换空间增长、GPU 设备与可用显存、后端限制、数据时间戳和可信度。安装时检查兼容性；每次任务开始及运行期间重新读取动态指标。

### 4.2 预算计算

对每个独立资源池分别进行检查，所有量统一以字节存储，界面再转换为 GiB：

```text
应用上限 = min(用户设置上限（如有）, 物理容量 - 系统预留, 平台允许上限)
应用余量 = max(0, 应用上限 - 本服务已占用 - 已预约但尚未分配的额度)
当前余量 = max(0, 平台可用估计 - 动态安全余量)
可准入额度 = min(应用余量, 当前余量)
本次新增峰值需求 <= 可准入额度，且压力正常、探测有效，才准许加载
```

系统预留用于限制应用最多能占多少；动态安全余量用于吸收其他软件增长和采样延迟。平台“可用内存”的定义由适配器记录，不把可回收缓存和 GPU 共享页重复计数。当前占用、未分配预约、增量需求必须分开记账，已经分配的预约不重复扣减。第一版卸载旧模型后再计算新任务需求，不依赖猜测旧模型可释放多少。

系统预留采用随容量变化的策略，并设绝对下限；不能用所有机器统一的 10、12 或 20 GiB 上限。具体预留比例、绝对下限和安全余量必须由硬件矩阵验证后定稿，见第 9 节。无论物理内存多大，第一版都遵守一个重型任务的限制。

### 4.3 模型需求档案

每个受支持的「模型版本 + 精度 + 后端 + 设备类型 + 任务配置」记录：

- 加载峰值、空闲驻留量、推理峰值、后处理峰值，以及各资源池的需求。
- 输入长度、输出时长、分段长度等对需求的影响及已验证边界。
- 最低运行需求、估计安全余量、测量平台、样本范围、版本和可信度。
- 是否支持低内存模式、分段、卸载，以及取消和退出的可靠性。

文件大小不能替代运行峰值。整条流水线取各阶段实际同时存活的资源之和，再取阶段最大值；不能只统计 Seed-VC 而漏掉 HTDemucs、参考人声处理和长音频缓冲区。

没有可用档案的配置不能自动开启推理。开发验收在受控环境建立档案，不让普通用户承担第一次大模型内存试验。模型、运行时或后端升级后，旧档案只有在验证兼容时才能复用。

## 5. 服务结构与执行流程

### 5.1 职责与所有权

```text
网页 / MCP / 内部工作流
          ↓
MusicService：业务任务与作品保存
          ↓
资源协调器：准入、排队、预约、加载/卸载、监控、回收
          ↓
IndexTTS 适配器 / YuE2 适配器 / 转换适配器 / 其他高负载任务适配器
          ↓
独立且受监管的工作进程
```

统一服务不意味着把所有模型装进同一进程。引擎适配器负责真实的启动、状态、取消和卸载；协调器负责决定何时允许执行。业务服务继续持有声音、版本和音频记录，协调器不复制业务数据库。

资源协调器放在 `src/service/resources/`，策略、硬件探测契约、任务预约及其测试就近组织；具体引擎适配留在对应引擎目录。先按职责组织文件，不预先引入通用插件框架。

网页、MCP、多项目和内部调用都必须经过协调器。YuE2 内部队列不得自行预取或加载未获准任务；持有额度必须持续到真实任务完成并完成所需释放，不能在 HTTP 提交返回后就释放。旧的引擎两两忙碌回调由共同队列替代，避免互相等待。

### 5.2 多服务实例

工作目录锁不能防止两个不同工作目录同时运行模型。第一版增加同一操作系统用户下的全局重型任务租约：同一时刻只有一个 Music Room 实例能加载或持有重型模型，其他实例显示“另一个工作区正在使用模型资源”。

租约记录拥有者、实例标识和所属进程身份；原子申请，正常退出释放。拥有者退出但模型子进程仍存活时，不能仅凭主进程 PID 消失就允许新实例加载。恢复只清理能验证归属的本应用进程，不按进程名称杀进程，不关闭其他用户的软件。空闲驻留不得无限占住全局租约。

不同操作系统用户的任务不依赖这把用户级锁互斥，仍由整机资源探测保护；不宣称已实现跨用户的全机唯一队列。

### 5.3 一次任务的流程

1. 校验输入与兼容性，按任务配置取得需求档案；明显无法运行的请求立即返回原因。
2. 保存业务任务和输入引用，进入有数量上限的队列。排队记录不预读整段音频、不启动推理进程。
3. 任务到达队首，申请全局租约；释放其他模型并等待进程真正退出。释放失败则阻止后续加载。
4. 重新采样硬件状态，以原子操作预约额度。提交检查不能代替此时检查，避免两个请求同时通过。
5. 在预约范围内加载与运行；阶段变化前复核需求。监控覆盖应用自身、模型进程树和整机压力。
6. 校验并提交结果；失败或取消不发布部分文件为成品。完成后释放任务临时预约；继续驻留的部分转为模型驻留记账，不能一并归零。
7. 有其他引擎任务时立即卸载；无任务时按空闲策略保留或卸载。仍驻留的模型持续记账并占有租约。

队列按提交顺序执行；已知永久不可运行的任务退出队列。队首因临时资源不足等待时显示原因，达到等待期限转为“等待用户重试”，释放队首位置；期限见第 9 节。新任务不抢占正在生成的任务。

### 5.4 状态与停止

任务主路径为 `queued → waiting_resources → loading → running → succeeded`，取消进入 `cancelling → cancelled`；资源不足且无法继续进入 `blocked`，执行错误进入 `failed`，服务重启发现未完成任务进入 `interrupted`。运行阶段可细分分离、转换和混音，但不引入多个独立资源拥有者。

取消先停止引擎任务，再等待实际进程或已验证卸载操作完成。优雅停止超时后终止本任务所属进程组；仍不能确认资源释放时，将该资源池标为不可继续使用，提示诊断，不能继续放行新模型。

“释放模型内存”首版以停止所属工作进程为可靠边界；若未来使用进程内卸载接口，必须测量证明确实释放了 CPU/GPU 工作集。仅清空 JavaScript 引用或收到“任务完成”都不算卸载成功。

服务退出先停止准入、取消队列和活动任务，等待子进程退出，再释放租约。崩溃后依靠所属进程监管和租约恢复清理；重启保留原输入，不自动重跑中断的重型任务。

## 6. 运行时保护与安装管理

### 6.1 运行时保护

保护同时依靠准入预估、后端可执行的分配限制、进程监管和整机压力采样。采样是事后保护，不能冒充瞬时硬内存上限；平台支持的硬限制也需要验证其覆盖 CPU、GPU 和子进程的范围。

| 信号 | 动作 |
| --- | --- |
| 压力升高但未危险 | 停止新任务准入，释放空闲模型与可回收缓存 |
| 持续危险压力、超过任务额度或交换空间快速增长 | 取消当前重型任务并释放所属进程，记录原因 |
| 内存分配失败、工作进程被系统终止 | 标为资源失败，清理残留，不自动重启 |
| 采样过期或读取失败 | 不启动新模型；运行中超过允许失联窗口则停止任务 |

采用恢复阈值和持续时间，避免压力在边界波动导致反复启停；灾难性超额可立即停止。首版不把“暂停进程”当作释放内存。CPU 线程数、后台优先级、下载和解压并发也应受控；GPU 使用率无法精确限额时如实说明，不显示虚假的百分比预算承诺。

### 6.2 安装、下载与磁盘

- 安装统一排队，第一版一次执行一个大型下载/解压/转换安装任务；与重型推理互斥，避免安装峰值漏算。
- 流式写入临时文件，分块校验；不将整个权重文件读入服务内存。
- 启动前检查目标磁盘：下载文件、解压或转换副本、最终文件和安全余量均计入；过程中继续检查，防止磁盘被其他软件写满。
- 支持受验证的断点续传与文件校验，成功后原子发布安装状态。取消保留可复用片段，清理规则明确。
- 删除缓存不删除作品、用户参考音频或仍被任务引用的模型。模型迁移和删除不得与使用该模型的任务并行。

## 7. 接口、记录与兼容

新增统一资源状态查询，供页面与 MCP 共用：硬件概况、预算来源、当前占用、采样时间、压力、当前任务、排队任务、等待原因和各引擎驻留状态。估计值与测量值明确区分。

业务任务保存现有输入和结果，再关联资源状态与原因码，例如 `INSUFFICIENT_CAPACITY`、`WAITING_FOR_MEMORY`、`UNSUPPORTED_BACKEND`、`RESOURCE_TELEMETRY_UNAVAILABLE`、`MEMORY_PRESSURE_ABORT`、`UNLOAD_FAILED`。用户看到浅显中文说明，诊断页保留模型版本、阶段、预计与实测峰值、终止原因。日志不重复写入原始文本和参考音频内容。

旧的安装目录与作品记录继续可读。旧的“自动启动 YuE2”设置迁移为引擎可用配置，不再授权绕过预算加载模型。旧启动接口保留兼容期，但也必须申请调度；状态查询和读取已生成音频不得触发模型加载。迁移不自动修改模型精度或创作参数。

## 8. 实施与验收

### 8.1 实施顺序

1. 先补统一调度的失败测试：三引擎竞争、常驻 TTS 切换、取消中加载、多实例竞争。
2. 建立资源协调器和适配器边界，把三引擎及辅助处理纳入生命周期，落实切换卸载与租约回收。
3. 实现当前支持平台的探测与监控，建立真实模型需求档案，再启用动态预算；移除各引擎互相冲突的独立预算决策。
4. 接入安装队列、磁盘检查、状态接口与设置页，迁移旧启动行为。
5. 完成自动化故障验证和受控真机测量，定稿数值策略，更新用户说明后发布。

### 8.2 可自动验证的行为

| 场景 | 必须成立的结果 |
| --- | --- |
| 三个引擎同时提交，来自网页与 MCP | 最多一个进入加载或执行，其他排队 |
| TTS 生成结束后提交转换或音乐 | 旧模型实际退出后新模型才启动 |
| 模型卸载超时或失败 | 后续任务不能启动，状态说明释放失败 |
| 8 / 16 / 24 / 32 / 64 GiB 等不同容量的模拟探测 | 采用实际资源池计算；没有固定 32 GiB 假设 |
| 独立显卡：内存足而显存不足，及其相反情况 | 两种都阻止加载，不将两池容量相加 |
| 同为 32 GiB，但整机当前占用不同 | 空闲机器可获准，压力机器等待；结果依需求档案判定 |
| 小内存机器无法容纳某模型 | 在启动前明确阻止，播放和作品管理可用 |
| 请求通过检查后，加载前内存减少 | 加载前复核阻止启动 |
| 取消排队、取消加载、取消推理、关闭服务 | 状态正确、任务不偷跑、预约和所属进程无泄漏 |
| 进程退出慢、后代残留、服务崩溃、多工作区竞争 | 不重复获得执行权，不误杀无关进程 |
| 监控失败、采样过期、内存分配失败 | 按规则阻止或停止，不把缺失指标当作空闲 |
| 长音频分离、转换、混音 | 计入主服务缓冲区与辅助模型，超过范围提前拒绝 |
| 磁盘不足、下载中断、校验失败 | 不发布完整安装状态，可恢复且不破坏作品 |
| 读取已完成音乐、查询状态、刷新页面 | 不加载模型，不改变队列顺序 |

策略测试使用可注入硬件探测和假进程；进程监管测试使用受控子进程，证明退出和清理事实。浏览器测试验证状态和操作，不能替代真实内存测量。

### 8.3 真机验收

至少覆盖最低拟支持容量、中等容量和高容量；在每类已支持后端测量冷加载、连续生成、最长允许输入、引擎切换、空闲释放、取消和人工制造的受控资源紧张。统一内存与独立显存分别验证；没有独立显存真机验收时，该后端仍标为未支持。

记录整机压力、应用与进程树峰值、显存峰值（适用时）、交换空间变化、释放耗时、任务结果和前台交互响应。模拟不同容量只能证明策略逻辑，不能冒充在 8 GiB 等真实设备上跑通模型。触及预设停止阈值就结束压力试验，不以把测试电脑压到失去响应作为验收方式。

## 9. 待商榷与发布门槛

以下数值不能凭当前开发机推定，需测量后补齐。没有定稿并验证前，不能宣称资源保护完成：

| 待商榷项 | 决策依据 |
| --- | --- |
| 系统预留比例、绝对下限、动态安全余量 | 不同容量机器的系统响应与模型峰值 |
| 各模型最低容量、输入边界及低内存配置 | 对应版本和后端的真实测量；不按权重大小推算 |
| 空闲驻留时长 | 连续生成体验、重新加载代价与其他工作区等待时间；压力升高时立即释放 |
| 采样频率、失联窗口、停止与恢复阈值 | 峰值上升速度、监控成本、误停率 |
| 优雅退出期限、强制清理期限 | 各运行时的真实取消和资源回收表现 |
| 队列长度与资源等待期限 | 任务记录成本、等待可见性与避免队首长期阻塞 |
| 各支持平台的可用内存口径与限制机制 | 平台适配实现、指标可信度与进程监管测试 |

确定的是统一管理、按实际硬件预算、默认串行和先释放后加载；这些规则不依赖上述数值即可先实现与测试。
